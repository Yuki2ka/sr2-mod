## The investigation: headless modding is genuinely feasible

I verified this against the actual tool sources rather than forum folklore.

**There is a real headless compiler.** `indiemagpie/RScript` documents `rsmc`, "a standalone console compiler, independent from RScript/RSON/GUI, that turns .rsm (with import/export) straight into .scr":

```
rsmc build <entry.rsm> -o <out.scr> [--lang-txt <Lang.txt>] [--lang-dat <Lang.dat>]
```

`.rsm` is a text DSL, so mods become **plain files in Git** — diffable, reviewable, no node-graph clicking. That's the whole basis for headless work.

**Source is text, all the way down.** The bundled `Example/` mod gave me the verified syntax for every construct a dialog mod needs:

| Construct | Verified form |
|---|---|
| Module entry | `scriptName("X");` + `import from './vars.rsm';` |
| Variables | `localVar("counter", "int", "");` — types `int/dword/str/unknown` |
| Hooks | `export function onGlobal() / onInit() / onTurn() / onDialogBegin()` |
| Dialog | `dialog("DialogPB6", {message: "DialogMsg19"});` or `{code: function() {...}}` |
| Text node | `dialogMsg("DialogMsg0", {text: "..."});` |
| Inject a menu item | `AddDialogInject('DialogPB1', '', "Когда я получу звание рейдер?", 1);` |

Files are UTF‑8 **with BOM**, CRLF. Code-object kinds are an enum in the `scird` decompiler: `NORMAL=0, INIT=1, GLOBAL=2, DIALOGBEGIN=3` — matching those four hooks exactly.

**The key insight that de-risks your request.** I initially assumed I'd need the science base's internal dialog name. I was wrong, and the example proves it: `DialogPB1`…`DialogPB6` are the *mod's own* dialogs, not the game's. The target is chosen by the surrounding guards, not by name:

```
if (GetShipRuins(Player()) > 0) {                        // docked at a station
    if (ShipType(GetShipRuins(Player())) == 'PB') {      // ...a pirate base
        AddDialogInject('DialogPB1', '', "...", 1);      // engine injects here
```

So for the science base I only need the same guard with the SB type token. Station codes are `SB` (science), `PB` (pirate), `WB` (military).

**One token remains unverified: `'SB'`.** `'PB'` is proven by the example; `SB` is a strong inference from the station-code list, but I could not run the game to confirm it. Rather than gamble, the mod below ships a **self-verifying probe** — a menu item that prints the real `ShipType` string at whatever station you're docked at, so your first playthrough tells you the exact value.

    if (GetShipRuins(Player()) > 0) {
        station_type = ShipType(GetShipRuins(Player()));

        // Probe: shows the REAL ShipType token for whatever station you dock at.
        // Read it once, confirm it matches SB_TYPE below, then set sb_probe=0.
        if (sb_probe) {
            AddDialogInject('DialogSbProbe', '', Format("SB probe: type=<0>", "<0>", station_type), 1);
        }

                AddDialogInject('DialogSbHello', '', "Спросить о текущих исследованиях", 1);

## The Windows runner

```python
#!/usr/bin/env python3
"""build.py -- headless SR2HD mod build. Run on Windows: python build.py"""
import argparse, re, shutil, subprocess, sys
from pathlib import Path

BOM, CRLF = "\ufeff", "\r\n"
IMPORT_RE = re.compile(r"""^\s*import\s+from\s+'([^']+)'""", re.M)

def validate_rsm(mod_dir: Path) -> list[str]:
    """Pre-flight checks mirroring the ones RScript fails on."""
    errs, seen, stack = [], set(), [(mod_dir / "main.rsm", [])]
    while stack:
        path, chain = stack.pop()
        if path in seen:
            continue
        seen.add(path)
        if not path.exists():
            errs.append(f"missing module: {path}"); continue
        raw = path.read_bytes()
        if not raw.startswith(BOM.encode()):
            errs.append(f"{path.name}: missing UTF-8 BOM")
        if b"\n" in raw.replace(b"\r\n", b""):
            errs.append(f"{path.name}: bare LF found, need CRLF")
        try:
            text = raw.decode("utf-8-sig")
        except UnicodeDecodeError as e:
            errs.append(f"{path.name}: not UTF-8: {e}"); continue

        # unbalanced delimiters / unterminated strings -- these hang RScript
        depth = {"(": 0, "{": 0, "[": 0}
        pairs = {")": "(", "}": "{", "]": "["}
        in_str = in_lc = in_bc = False
        for i, ch in enumerate(text):
            two = text[i:i+2]
            if in_lc:
                if ch == "\n": in_lc = False
                continue
            if in_bc:
                if two == "*/": in_bc = False
                continue
            if in_str:
                if ch == '"' and text[i-1] != "\\": in_str = False
                continue
            if two == "//": in_lc = True; continue
            if two == "/*": in_bc = True; continue
            if ch == '"': in_str = True; continue
            if ch in depth: depth[ch] += 1
            elif ch in pairs: depth[pairs[ch]] -= 1
        if in_str: errs.append(f"{path.name}: unterminated string")
        if in_bc:  errs.append(f"{path.name}: unterminated block comment")
        for op, n in depth.items():
            if n: errs.append(f"{path.name}: unbalanced {op!r} ({n:+d})")

        if path.name != "main.rsm" and "scriptName(" in text:
            errs.append(f"{path.name}: scriptName belongs in main.rsm only")

        for rel in IMPORT_RE.findall(text):
            target = (path.parent / rel).resolve()
            if mod_dir.resolve() not in target.parents:
                errs.append(f"{path.name}: import escapes project: {rel}")
            if target in chain:
                errs.append(f"{path.name}: import cycle via {rel}")
            stack.append((target, chain + [path]))
    return errs

def main() -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("--mod-dir", type=Path, default=Path("mod/SbHello"))
    ap.add_argument("--rsmc", type=Path, default=Path("rsmc.exe"))
    ap.add_argument("--game", type=Path, help="SR2HD install root")
    ap.add_argument("--lang", default="Rus", choices=["Rus", "Eng"])
    ap.add_argument("--deploy", action="store_true")
    a = ap.parse_args()

    errs = validate_rsm(a.mod_dir)
    for e in errs: print(f"ERROR {e}", file=sys.stderr)
    if errs: return 1
    print(f"validated {a.mod_dir} -- ok")

    build = Path("build"); build.mkdir(exist_ok=True)
    script_name = re.search(r'scriptName\("([^"]+)"\)',
                            (a.mod_dir / "main.rsm").read_text("utf-8-sig")).group(1)
    scr = build / f"{script_name}.scr"
    lang_txt = build / f"{script_name}_lang.txt"

    cmd = [str(a.rsmc), "build", str(a.mod_dir / "main.rsm"), "-o", str(scr),
           "--lang-txt", str(lang_txt)]
    print("run:", " ".join(cmd))
    subprocess.run(cmd, check=True)
    print(f"built {scr}")

    if a.deploy:
        if not a.game: ap.error("--deploy needs --game")
        dst = a.game / "Mods" / script_name
        (dst / "Data" / "Script").mkdir(parents=True, exist_ok=True)
        (dst / "CFG" / a.lang).mkdir(parents=True, exist_ok=True)
        shutil.copy2(scr, dst / "Data" / "Script" / scr.name)
        print(f"deployed to {dst}")
        print(f"NEXT: merge {lang_txt} into {dst}/CFG/{a.lang}/Lang.dat "
              f"under Script/{script_name} (BlockParEditor), "
              f"add ModuleInfo.txt, and set CurrentMod={script_name} in Mods/ModCFG.txt")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

## ADDENDUM (second pass) — open questions closed, mod written

Everything above still stands as the feasibility case. This pass turned the
draft into a real, lint-clean project and closed most of the "still open" list.

### Resolved

**1. `'SB'` is the Science base. Two independent machine-readable sources.**
   - sr-modkit ships `data/lexicon.json`: 977 functions with descriptions and
     arity, built from a corpus of 330 decompiled SRHD mods (183 657 observed
     calls). Its `ShipType` examples are verbatim real code, and the first is
     `if(ShipType(GetShipRuins(Player()))=='SB' || ShipType(GetShipRuins(Player()))=='CB')`
     — the exact shape we need, from a working mod.
   - `rsmc`'s own VS Code grammar (`rsmc.rsm-language-0.1.0`) enumerates the
     built-in constants and contains `t_SB` alongside `t_PB`, `t_UB`, `t_WB`,
     `t_RC`, `t_MC`, `t_BK`, `t_CB`.
   The probe is kept anyway (off by default, `vProbe = 1`) because it costs
   nothing and answers the question in one playthrough if `'SB'` is wrong.
   Details and the full token table: docs/STATIONS.md

**2. `AddDialogInject` semantics.** XenoModKit issue #17 quotes the engine
   sources: the first argument lands in `Entry.DialogName` and is used only when
   the injected answer is clicked — it is a **jump target**, not the injection
   target. The item is added to whatever station menu is open, so the target is
   chosen by the surrounding guards (`GetShipRuins(Player()) > 0` +
   `ShipType(...) == 'SB'`), exactly as the first pass guessed. Full signature
   (arg1 dialog, arg2 greeting add, arg3 answer text, arg4 priority) confirmed
   by `data/lexicon.json`.

**3. Only one Windows-only dependency: `rsmc.exe`.** New find —
   https://github.com/ArtYudin89/sr-modkit is a pure-Python toolkit that
   scaffolds (`srmod new`), lints against a schema extracted from `rsmc.exe`
   itself, builds (`srmod build`), and deploys (junction). It writes
   `Lang.dat`, `Main.dat` and `CacheData.dat` with its own vendored BlockPar
   implementation, so BlockParEditor is out of the loop entirely. It only shells
   out to `rsmc.exe` for `.rsm -> .scr`. Chosen as the primary pipeline;
   XenoModKit stays as the optional auditor.

**4. Encoding rule corrected.** The first pass said ".rsm is UTF-8 with BOM,
   CRLF" (true of the RScript `Example/` files). sr-modkit refuses a BOM
   outright (`assert_rsm_is_utf8`). Rule now: `.rsm` = UTF-8 **without** BOM,
   `src/**/*.txt` = **UTF-16LE + BOM**. `tools/compile.py --fix-encodings`
   enforces both, and its preflight reproduces sr-modkit's gates with
   actionable messages.

**5. The Lang.dat merge is not hand-rolled any more.** `srmod build` stages a
   `Lang.txt` containing an empty `Script ^{ SbHello ^{ } }` skeleton, lets
   rsmc merge its `text:` table into it, then converts the result to
   `Lang.dat` itself. The old draft's "merge the TXT into Lang.dat with
   BlockParEditor by hand" step is gone.

## ADDENDUM (third pass) — why the probe appeared only once

### User report

In the test, the probe items appeared while docked at the starting Ranger
Centre (RC). After undocking and docking again, neither probe nor the Science
base item appeared. The player starting at RC was suspected to be the cause.

The RC start is normal and is not the cause. `vProbe` deliberately runs at any
station, so an initial `RC` result is useful: it proves the script started and
the dialog hook ran, but of course it does not test the `SB` condition. The
missing later probe was a script-lifetime bug.

### Root cause, traced in the reverse-engineered game source

I checked the relevant paths in
[`pakompom/SpaceRangersHD_decomp`](https://github.com/pakompom/SpaceRangersHD_decomp)
(the source is reverse-engineered, not an official game SDK):

1. `source/screens/fRuinsTalk.pas` builds station choices by calling
   `RunDialogCode` on each active entry in `Galaxy.Scripts`. Therefore the
   `onDialogBegin` hook is able to add its item again each time a station menu
   is built, provided the script instance is still active.
2. `source/game/aGalaxy.pas` runs each active script at end of turn, then
   deletes it when `Script.Ships.Count < 1`. It also clears the template's
   `ActiveScriptIndex`, so that template can be considered for a later start.
3. In `source/script/aScript.pas`, `ship({player: true, ...})` is a star-level
   ship requirement used when starting/matching a script; it does **not** add a
   ship binding to `Script.Ships`. The group loader calls `BindShip(...,
   GetPlayer)` only for a group with `addPlayer: true` (`IncludePlayer`).
4. `GCntRun` reads the template's accumulated `UseCount`. It is not a query for
   whether an instance is currently active. The old `onGlobal` guard
   `if (!GCntRun(GScriptName)) GRun();` therefore starts only once. Once the
   empty group caused the instance to be deleted, the nonzero run count blocked
   its restart.

That matches the symptom: first station opens, the script starts and injects
its probe; after the zero-ship instance is collected at the end of a turn, the
next dock has no active script to run `onDialogBegin`. The player's RC spawn is
independent of the Science-base condition, and changing the spawn location is
neither necessary nor desirable.

### Fix applied

`world.rsm` now declares `SbGroup` with `countMin: 1`, `countMax: 1`, and
`addPlayer: true`. The engine subtracts the included player from the number of
NPCs to create, then binds the player, so the group has one member and does not
spawn an extra ship. Its `SbIdle` state is intentionally inert. This keeps the
script active after its first turn, while `GCntRun` still correctly prevents
reinitializing the one-time script.

I also updated the source comments and the workflow/station/lifecycle notes so
future edits do not turn this into a zero-ship group again. The diagnostic flag
remains enabled; at RC the probe may report `RC`, while at a Science base it
should report `SB` or `CB` and the research option should be visible.

### Verification still required

The lifecycle explanation is source-reviewed against the reverse-engineered
files above, not proven by a new game run. The updated `.rsm` passes
`python tools/compile.py --stage lint --srmod-root <sr-modkit-root>` here; this
sandbox has no Windows `rsmc.exe` or game. Rebuild and deploy the current
revision on Windows, start a **new** game, confirm the probe at RC, travel to a
Science base and confirm the probe and research option there, then undock/redock
to verify they recur. See `docs/VERIFICATION.md`.

## ADDENDUM (fourth pass) — iteration without a new game, and «Проходит время»

Player report that started this pass: the mod works ("i tested and it works"),
but starting a new game for every change is unacceptable, and the new-game phase
«Проходит время» is slow — the player knows mods that make it *longer* to start
a game several years later, so a knob must exist.

Both questions were answered from the reverse-engineered engine
([`pakompom/SpaceRangersHD_decomp`](https://github.com/pakompom/SpaceRangersHD_decomp),
SRHD 2.1.2500). Long form with every citation: **docs/FAST_ITERATION.md**.

### Q1. Can the mod change without a new game? — YES

The claim repeated in earlier notes ("mods require a new game") is **wrong** and
has been removed from the docs. What actually happens on a save load
(`aSaveLoad.pas LoadGameFromSaveBuffer` → `TGalaxy.LoadFromBuffer`):

1. Saved script templates are matched **by name**; a template that is gone only
   logs `Warning: Script not found - <Name>` and the instance is skipped.
2. Shared script variables are restored **by name** (`GetVarNE`); an unknown
   saved variable is a warning, not an error.
3. Each saved instance calls `TScript.LoadState` (`$657690`), whose **first
   statement is `LoadFromFile(ScriptFileName)`** (`$656D1C`) — the `.scr` is
   re-read from disk on every load, and `LoadFromFile` evicts its `GlobalCache`
   entry in a `finally`, so no stale copy survives. `TScript.SaveState`
   (`$656E90`) states it plainly: compiled instructions are not saved.
4. Stars/planets/items/ships are rebound **by name** (`GetStar` raises if the
   star is gone — this is the one way to break an existing save).
5. `Galaxy.RunConfigOnLoadHandlers` (`aGalaxy.pas $7A3A2C`, called from
   `aSaveLoad.pas:270` and `:590`) executes every sub-block of
   `MainDataConfig.BV/OnLoad` as script text (`ConcatenateValues`, `$8499BC`).

Config reload without restarting the exe: `Rangers.dpr:690-745` re-runs
`LoadDatConfigAndModOverrides` (`GR_Main.pas $4CC738`) plus runtime re-init,
ship-state refresh and import rebinding whenever `ReloadScriptTemplates or
ReloadModsRequested`; «Применить» in the mod manager (`fMods.pas:884
ApplyClick`) writes `Mods\ModCFG.txt` and raises that flag. A save whose mod set
differs is **not** rejected — `aGalaxy.pas:1400-1410` only logs
`Warning! Mod sets mismatch:`.

So the loop is: edit `src/` → `tools\run_compile.cmd` → (Mods → «Применить» only
for config changes) → **load the same save**. One new game, ever, per campaign.

Fix applied: `mods/SbHello/src/CFG/Main.txt` now carries the hooks that make
this work for a save that predates the mod —

```
BV ^{
    OnStart ^{
        0DayScripts ^{
            SbHello=ScriptRun(ShipStar(Player()), GetShipPlanet(Player()), 'SbHello');
        }
    }
    OnLoad ^{
        Runtime ^{
            01=if(!IsScriptActive('SbHello')) ScriptRun(ShipStar(Player()), GetShipPlanet(Player()), 'SbHello');
        }
    }
}
```

(the DAT text form: `^` = sorted block, as `srmod new` writes it; the parameter
names inside a handler do not matter, `ConcatenateValues` drops them and joins
the values)

`OnStart` fires at generation `Stage := 16` (see Q2), `OnLoad` on every save
load. The guard is mandatory: `SF_ScriptRun` (`$61EB20`) matches
`ScriptFileName` first and otherwise creates an instance unconditionally
(`TryStartScriptInstanceFromTemplate`, `aScript.pas:1112`), so an unguarded
`OnLoad` would start a second instance per load. The old `onGlobal`/`GRun()`
path is kept only as a fallback, and its `GCntRun` guard is gone (third-pass
finding: `UseCount` is saved, so the guard blocked restarts forever).
`SF_GRun` (`$605480`) merely sets `ScriptTemplateStartRequested`, so an
unguarded `GRun()` is safe.

Related gotcha now documented: **variable values are part of the save**, so
`vProbe`'s initial value in `vars.rsm` applies to new games only; on a loaded
save the stored value wins. `code.rsm` gained `vStartTurn = CurTurn()` in
`onInit` and prints it in the probe (`type=<0> start=<1> now=<2>`), which turns
the whole question into a one-dock experiment: `start=0 now=301` = new game via
`BV/OnStart`; `start=0 now=<save turn>` = instance restored from the save, no
new game needed; `start=<turn> now=<turn>` = `BV/OnLoad` created the instance.
(301 and not 300: `Galaxy.CurrentTurn` starts at 0 — `aGalaxy.pas:1028` — every
`Galaxy.NextDay` increments it — `:2340` — and `Stage := 17` runs one
`CalculateGalaxyTurnAndWait` before the 300-iteration warmup loop.)

### Q2. Can a mod skip «Проходит время»? — NO, but it can shrink it

Identity of the phase, pinned down structurally (the Russian label appears
nowhere in the code): `TThreadCreateNewGame.Execute` (`screens/fGameSettings.pas`)
runs

```pascal
Stage := 16;
Galaxy.RunConfigOnStartHandlers;      // BV/OnStart — mods get control here
NewGameGenerationStage := 6;          // the label «Проходит время» (fIntroduction.pas:208)
Stage := 17;
CalculateGalaxyTurnAndWait;
for I := 1 to GalaxyWarmupTurns do    // GalaxyWarmupTurns = 300, aGalaxyStruct.pas:7
begin
  if I mod 20 = 0 then SysUtils.Sleep(1);
  CalculatePlayerStarTurnAndWait;
  CalculateGalaxyTurnAndWait;
end;
Stage := 18;  // dock at the RC, starting skills and equipment
Stage := 19;  // ApplyCharacterPreset, RunGlobalScriptsForContext(star, 0), stage := 8
```

`Stage` (0..19) is internal and appears in the crash log
(`Galaxy create exception, label = <Stage> seed = <seed>`);
`NewGameGenerationStage` (0..8) drives the intro screen. 300 turns at
`TurnsPerYear = 365` is ~300 days of simulated history, and the calendar is
defined around it: `TGalaxy.TurnToDateTime(Turn) = Turn + 511341.5 -
GalaxyWarmupTurns`, with gameplay gates comparing against the same constant
(`Achievements.pas:427`, `aGalaxy.pas:2301/2453/5414`). Independent
corroboration that this is the phase mods hang on: XenoModKit's README and
`SCRIPTING_GUIDE_RU.md` both describe «зависание на "Проходит время"».

Every door checked, all closed:

- The bound is an immediate constant; no `Main.dat` / `Lang.dat` /
  `CacheData.dat` / `newgame.txt` key reads a warmup or history length
  (`newgame.txt` CustomRules has `KlingStrength/KlingAggro/KlingSpawn/
  PirateAggro/CoalAggro` … and no turn count).
- `Galaxy.StasisModEnabled` is the one flag that makes warmup turns nearly free
  — `TThreadCalc.Execute` (`ThreadCalc.pas $7E4BC4`) wraps the whole
  `Galaxy.NextDay` block in `if Galaxy.StasisModEnabled <> 1`. It is written in
  exactly three places: init to 0 (`aGalaxy.pas:871`), save load
  (`:1771/:1778`), and the **`ZAWARUDO` cheat** (`CheatCode.pas:1509`). It is
  saved with the galaxy and clears the "clean game" flag (`aGalaxy.pas:4287`),
  i.e. a cheat, not a knob.
- No script function can set it: all 755 `Scope.Add` registrations were scanned;
  the only galaxy field any function writes is `CurrentTurn`
  (`SF_CurTurn`, `$608800`: `if High(av) > 0 then Galaxy.CurrentTurn := av[1].GetInt`).
  `GalaxyPtr('StarCnt')` yields an address but nothing writes through it.
- `ExitScreenLoop` is the window-close path: `Exit` inside the loop skips
  `Stage := 18/19` (docking, starting equipment, `ApplyCharacterPreset`,
  `RunGlobalScriptsForContext`) and never sets `NewGameGenerationStage := 8`, so
  the intro screen would hang forever.
- `ForceNextDay()` only sets `ScriptEndTurnRequested`, dispatched by the UI
  (`TryDispatchScriptEndTurn`) — meaningless during generation.
- `loadlibrary`/`libraryfunction` could in principle patch the constant, but
  Delphi evaluates a `for` bound once at loop entry, so it would have to land
  before `Stage := 17`; shipping a version-specific memory patch is not modding.

What *is* moddable is the cost of each of those 300 days. `TGalaxy.NextDay`
(`aGalaxy.pas:2310-2360`) loops `Star.NextDay(False)` over every star, runs
script Turn/Global code, then stations, constellation stats, prices, ranger
quotas and `RefreshTechLevel` — so fewer stars means cheaper turns, and the mod's
own `onTurn`/`onGlobal` run 300 times there (keep them O(1); a heavy per-turn
script is exactly what hangs this phase for other mods).

The lever: `aConst.pas:1491 InitializeGameplayConfig` — called from
`InitializeGlobalUiRuntime` (`Globals.pas:675`, ~`:1194`) **after**
`LoadDatConfigAndModOverrides` — reads `Constellations.GalaxyCountStars` (**73**),
`GalaxySizeY` (**100**) and `GalaxySizeX` (**145**) from `LanguageDataConfig`,
i.e. from the merged `CFG\Rus\Lang.dat`. Merge semantics
(`TBlockParEC.MergeFrom`, `EC_BlockPar.pas:1299-1359`): same-name **blocks**
merge recursively, same-name **params** are deleted then re-added — the mod wins
without destroying its neighbours. Community precedent for the very same key:
`RefABitMoreStars`/`5`/`10` (+10/15/20 star systems) and `FairanGalaxy`
(+11 star types, +70 background systems), all Lang-only mods.

So `mods/FastGalaxy` was created: script-less (`"script": {"engine": "none"}`,
supported by `srmod/build.py:737`; `srmod new` cannot scaffold one), one
override `Constellations { GalaxyCountStars = 45 }`, heavily commented, opt-in,
new games only. Expected: ~38 % fewer stars ⇒ roughly 2-3× faster generation
(estimate, not measured) and a smaller galaxy to fly in afterwards.
`GalaxySizeX/Y` stay vanilla, so map geometry is untouched. Known risk:
`ConstellationCount := 20` is hardcoded (`aGalaxy.pas:821`) and
`GenerateGalaxyLayout` (`:6207-6249`) divides the map into 20 polygons, so a too
low star count yields sparse constellations — raise to 55/60 or disable the mod
if the galaxy looks wrong; a generation failure logs
`Galaxy create exception, label = <Stage> seed = <seed>`.

Honest framing for the player's premise: mods that "make this phase longer to
start the game years later" cannot be changing the turn count — the constant is
not data. Either they make each turn more expensive (more stars/stations/ships),
or they move the calendar with `CurTurn(N)` from a `BV/OnStart` handler, which
changes the displayed date and every `CurrentTurn` gate without simulating
anything. SbHello deliberately does not do the latter: it desynchronises the
date from the real state of the galaxy.

### Bonus: open question 3 from the first addendum is resolved

`'CB'` is **not** a Science-base variant. `GetTypeNameKey` is
`ShipTypeNames[TypeId].Name` (`aShip.pas:2197`), `ShipTypeNames` is
`array[TShipType]` (`aConst.pas:381`) and `TShipType` is enumerated at
`aGalaxyStruct.pas:75-90`, so lining them up gives the exhaustive table:
0 `Kling`, 1 `Ranger`, 2 `Transport`, 3 `Pirate`, 4 `Warrior`,
5 `Tranclucator`, 6 `RC`, 7 `PB`, 8 `WB`, 9 **`SB` = `rstScienceBase`**,
10 `BK` = business centre, 11 `MC` = medical base, 12 **`CB` = `rstDominion`**,
13 `UB` = custom station. The corpus line that motivated `|| 'CB'` is a mod
serving two station kinds on purpose, not evidence about `SB`. `onDialogBegin`
now tests `vStationType == 'SB'` only; docs/STATIONS.md carries the table.
Corpus tokens like `'TC'`, `'AS'`, `'MB_licensed'` are not in the table at all —
mods may set type names at runtime, so any string can appear.

Also useful for testing, from the same routine: generation stage 14 creates the
ranger centre, the **science base** and the medical base **in the player's
starting system** (pirate base at `StarDistances[3]`, business centre at `[1]`,
military base at `[2]`) — the Science-base dialog needs no flying.

### Tooling changes in this pass

- `tools/compile.py`: preflight step **4b `check_main_dat`** parses
  `src/CFG/Main.txt` with sr-modkit's vendored `srblockpar` and catches the four
  ways a `BV` hook silently fails — `//` inside a value (checked on the **raw**
  text, because both parsers strip it before the tree exists), a param named
  `BV` (clobbers `BV.BV = 2.1.2500`, `GR_Main.pas:2983`), an empty or
  block-less handler, `ScriptRun('<name>')` not registered in `Data/Script`, and
  an unguarded `ScriptRun` in `OnLoad` — and prints the concatenated text of
  every hook, exactly what the engine will execute. `check_script_name` now
  skips config-only mods instead of failing them.
- `tools/run_compile.py`: `MOD_DIRS` replaces `MOD_DIR`; the front-end builds
  every listed mod, survives a failure in one (`compile.py`'s `die()` raises
  `SystemExit`), pauses only after the last, and returns the worst exit code.
